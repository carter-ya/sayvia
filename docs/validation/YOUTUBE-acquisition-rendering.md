# YouTube 字幕获取与替换显示研究

> 历史研究记录：当前决策和后续真实验证见 [实现契约](../LEARN_IMPLEMENTATION.md) 及 [审核记录](LEARN-review-log.md)。保留本轮失败结果，不把旧候选状态当作当前结论。

- 日期：2026-11-03。
- 结论：优先验证“复用播放器的字幕响应 + Sayvia 独立字幕层”。这是实现选型，不是已经通过实站验收的功能。
- 证据范围：官方文档、公开项目源码审查、当前仓库集成检查；沿用[首轮实站记录](YOUTUBE-feasibility.md)，本轮没有新增真实字幕捕获或覆盖层运行结果。
- “替换”指当前观看页面的字幕显示，不修改视频文件，也不上传或修改作者字幕。

## 1 推荐路径及证据强度

```text
YouTube 正常加载用户可观看的原文字幕
    → 在页面中旁路读取该响应，不重发字幕请求
    → 校验视频／轨身份，解析带起止时间的 cue
    → 隔离脚本维护时间轴，现有模型执行器分批提前翻译
    → 按 video.currentTime 显示 Sayvia 字幕
    → 接管显示时隐藏原生字幕外观，退出／失败时恢复
```

沉浸式翻译的官方说明明确描述：默认流程尽量复用 YouTube 播放器已经获取的原文字幕，再交给用户选择的翻译服务，以减少额外字幕请求。这支持优先选用“复用已有响应”的工程方向，但不证明其内部具体采用 fetch 包装，也不是 Sayvia 的成功率证据。[S1]

本轮实际读取了 SubTwin 的 `page-bridge.js`、`youtube-native-caption-controller.js` 和 CSS：前者包装 fetch／XHR，旁路读取 timedtext 响应；后两者通过播放器局部 class 隐藏原生字幕容器。它证明这些实现模式已有公开代码。该项目 README 同时承认私有接口会变化，部分视觉行为尚未实站验证；不能把它当作生产稳定性背书，也不直接移植其实现。[S2]

不存在能保证任意公开视频、任意账号和网络都稳定获取字幕的普通观众官方 API。当前目标应是：在原生字幕可用的前提下尽量复用同一响应，减少请求差异，并在不可用时准确降级。

## 2 获取方式对比

| 方式 | 可获取未来字幕？ | 主要限制 | Sayvia 决策 |
| --- | --- | --- | --- |
| 旁路读取播放器已收到的 fetch／XHR 字幕响应 | 取决于响应覆盖范围，可包含后续 cue | 必须足够早安装；播放器内存缓存、其他执行上下文及站点改版可能使包装失效 | 主路径原型 |
| 复制字幕 URL 后自行请求 | 成功时可以 | 依赖会话、参数、有效期及服务端策略；首轮独立请求为空正文 | 不作为首期主路径，不后台不断重试 |
| 标准 `video.textTracks` | 如果平台提供完整 cues 则可以 | 首轮 YouTube 实测为空；并非所有播放器都暴露 | 通用视频适配的优先探测项，不能作为 YouTube 保证 |
| YouTube 文字稿面板／内部文字稿接口 | 可能提供较长文本 | UI、参数和可用性会变；可能只有起点而无可靠结束时间；首轮面板持续加载 | 可选诊断／后续补充，不作为隐藏回退链 |
| 观察屏幕上当前字幕 DOM | 通常只有当前文字 | 得到时已到播放位置，没有可靠前瞻，模型耗时直接成为延迟 | 当前句翻译是另一种体验，不能冒充同步双语 |
| 官方 `captions.download` | 是 | 要求用户有视频编辑权限 | 不适用于普通观众场景 [S3] |
| `webRequest`／请求规则修改 | 不能凭请求事件取得正文 | Chrome webRequest 暴露请求生命周期和响应头等，不提供通用响应正文读取接口 | 不为此新增权限 [S4] |
| 服务端字幕代理／下载工具 | 取决于上游 | 把获取问题搬到另一环境，并增加服务、隐私及维护依赖 | 首期不引入 |
| 音频识别生成字幕 | 可以生成另一份字幕 | 需要音频访问、识别费用、时延与新授权流程 | 超出当前首期 |

yt-dlp 的维护者文档将字幕列为部分客户端需要 Proof of Origin 的请求类别，说明请求可能与客户端验证上下文有关。它不能证明首轮 HTTP 200 空正文就是某个令牌导致；不据此设计猜造令牌、导出登录 cookie 或修改身份的补救链。[S5]

## 3 主路径如何提高可靠性

### 3.1 注入时机、授权和已有页面

当前 `src/background/site-access.ts` 在 `document_idle` 注册通用隔离内容脚本。直接在那里监听，可能错过首次字幕请求。新增仅匹配 `https://www.youtube.com/*` 顶层文档的轻量 MAIN world 脚本，在 `document_start` 安装监听；使用整站路径是为了覆盖从首页经站内导航进入视频的情况。站点访问仍由 Chrome 已授予的权限决定。主 UI、模型调度和解析留在隔离环境，Key 继续只在可信扩展上下文中。[S6]

早安装监听不等于自动收集或翻译：未启用时不缓存／转发字幕正文，开启后只接收当前视频和源轨。启用状态由扩展侧管理，网页消息不能开启付费翻译。

**中途开启是主要待验证风险。** 已经进入播放器内存的响应不会因为安装监听而重放，重新打开 CC 或选择同一轨也不保证发请求。启用后先等待正常字幕加载；若仍没有未来 cue，提示在原生设置选择源语言轨，必要时由用户刷新页面重试。不得自动反复切轨、刷新，或宣称刷新必定恢复。刷新后的启用握手是否赶得上首次请求也必须实测；不能用默认保存所有观看字幕来掩盖这个问题。

### 3.2 只读响应，不干扰播放

- fetch：保留原请求参数、返回值和错误语义；观察原 promise 的结果，及时克隆匹配响应并异步读取，不等待解析／模型再交给播放器。不改 URL、headers、签名或响应内容。
- XHR：兼容实际观察到的 responseType，在请求结束后读取；用独立元数据关联每次请求，处理同一个 XHR 对象复用、失败、取消和监听清理，不能不断叠加监听。
- 匹配 URL 使用明确 origin 和 pathname 白名单，起始候选是已观察到的 YouTube timedtext 路径；校验最终响应地址。不能仅使用字符串包含 `timedtext`，不接收网页指定的任意 URL。
- 保留视频 ID、源轨身份、语言、人工／自动类别及请求发起时的会话版本。只传递这些字段和必要正文；不传完整签名 URL、cookie、令牌或其他页面响应。
- 原型候选上限：单响应解码字节 4 MiB、当前视频所有字幕及译文文本累计 8 MiB、规范 cue 20,000 条、单条文本 4,000 Unicode 码点；先达到任一限额即停止扩展侧处理并提示，不能静默把截断时间轴当成完整数据。数值是待实测调整的预算，不是视频覆盖承诺。
- fetch 克隆分支立即以有界流读取，超限／超时取消自己的 reader；不取消原请求。仅在 `.text()` 完成后检查大小不够，`Response.clone()` 的慢分支可能缓冲大量数据。[S7] XHR 已由播放器缓冲的响应无法追回，但扩展须在解析和复制前限制额外内存。
- 页面可能提前保存原生函数、改用 Worker 或其他加载途径；这时 MAIN 包装也可能读不到。检测无数据并保持原生字幕，不把旁路读取描述成浏览器级全覆盖。

### 3.3 数据桥接与时间轴

MAIN world 和网站共享环境。`postMessage` 的来源标记、随机 channel 或同 origin 检查均不能让网页数据变成可信数据。隔离侧校验协议、字段、载荷大小、频率、当前视频／源轨；后台依据真实扩展 sender 的 tab／document 身份及用户启用状态决定能否请求模型。页面数据不能设置模型地址、Key 或创建任意任务。

JSON3、srv3/XML、WebVTT 是待覆盖格式候选；按实际响应识别解析器，不为方便解析而重发改格式请求。缺失／非法时间、未知结构、空正文分别报告，不能都叫“无字幕”。XML／字幕标签只提取文字，展示使用 textContent，不把字幕 HTML 插入页面。

自动字幕可能滚动追加、重叠或修订。保留窗口／事件身份与文本版本，不能将每个碎片机械相加，也不能按相同文字全局去重。只把规范 cue 文本及 ID 交给模型，时间戳留在本地；修订时使受影响译文失效。

记录实际已取得时间范围；只取得部分时间轴时，不声称能预翻译整段视频。翻译候选窗口为播放点后 30～60 秒，限制批次字数与最大前瞻；按字幕密度和倍速调整。此前六次自制夹具计时支持继续验证，不是持续播放速度保证。

视频、轨、广告状态或播放器节点变化时，暂停接管并清空活动 cue；视频／轨切换推进会话版本，丢弃迟到响应。不能只在网络响应返回时读取当前页面 URL，否则旧视频响应可能串到新视频。

## 4 替换显示：独立字幕层 + 可恢复的局部隐藏

| 显示方式 | 结果 | 决策 |
| --- | --- | --- |
| 直接改写原生字幕 DOM 文字 | 容易被播放器下一次更新覆盖；与自动字幕修订竞争 | 不采用 |
| 改写字幕网络响应，让原生播放器显示译文 | 必须等待译文或持续改写内部数据；容易阻塞原生加载 | 不采用 |
| 调用私有播放器接口注入新轨 | 没有受支持的稳定扩展契约 | 不作为核心依赖 |
| Sayvia 自绘字幕，局部隐藏原生字幕外观 | 时间轴和样式可控，可双语／仅译文，可独立恢复 | 推荐原型 |

覆盖层置于当前播放器容器内部，用 Shadow DOM 隔离自身样式。原生字幕容器在 Shadow DOM 外，隐藏它需要独立、播放器局部的 CSS 规则。候选选择器为 `#movie_player .ytp-caption-window-container`，属于站点私有细节，必须单独封装和实站检测。[S2]

建议原型用 Sayvia 专用 player class + `visibility: hidden` 隐藏原生字幕外观，保留原生 CC 功能和节点；不要点击关闭 CC 来“隐藏”字幕。CSS 隐藏是否影响该版本播放器的加载／布局行为仍要实测。关闭或恢复时仅移除 Sayvia 的 class、样式和节点，不覆盖用户原先的 inline style，也不强制将 CC 打开。

接管条件为：源轨与当前视频一致、该时间范围的原文可用、覆盖层已挂载且可见、非广告或未知播放器状态。默认双语；提供“仅译文”作为显示切换。译文未就绪时双语模式显示当前原文及等待状态；仅译文模式临时恢复原生字幕并提示等待。解析／渲染失败、播放器重建、退出时立即恢复原生显示，避免黑屏式“字幕全没了”。字幕空档不保留上一句。

同步以 `video.currentTime` 为准；播放中优先使用 `requestVideoFrameCallback` 的媒体时间，未支持时使用动画帧及媒体事件回退。暂停、seeked、ratechange、恢复可见时立即重算，暂停期间不持续轮询。不能用墙上时钟累加，否则跳转和倍速后易漂移。[S8]

全屏时检查真实 fullscreenElement，保证覆盖层在显示视频的全屏容器内；播放器替换时重新挂载，先清理旧容器的隐藏状态。覆盖层默认不拦截播放／进度操作，仅字幕选词交互区域接收指针；影院、尺寸变化、长字幕及控制条避让分别验收。普通视频画中画不会自动携带这层页面 DOM，首期继续不声明支持。

恢复必须覆盖三类路径：正常关闭；站内导航／播放器重建；扩展更新／上下文失效。Chrome 注销内容脚本不会自动删除已注入的脚本和样式，需显式清理；若原型不能证明失效时自动恢复，必须记录限制并提供刷新恢复入口，不能承诺所有异常都已解决。[S6]

## 5 最小验证及通过门槛

L00b 先做独立最小原型：观察响应 → 打印脱敏 cue 统计 → 用原文重绘与恢复 → 再接真实模型。先证明字幕数据和可恢复显示，再投入完整字幕设置面板。

| 实验 | 必须记录的通过证据 |
| --- | --- |
| 人工轨／自动轨 | 至少两个不同公开视频，各覆盖可用人工／自动轨；真实正文非空，有合法起止时间和超出当前画面的后续 cue |
| 已打开页面／新打开页面／首页站内进入 | 分别记录启用时机、是否需要刷新、首次可用延迟；只测新加载不算已有页面通过 |
| 选择与切换源轨 | 请求身份对应当前选轨；从 YouTube 自动翻译轨回到原文轨时没有误标或双重翻译 |
| 仅重绘原文 | 隐藏原生外观后原生字幕请求及播放仍正常；关闭恢复，没有重复／永久隐藏；保留截图或录像 |
| 0.5／1／2 倍速、暂停、跳转 | 以真实 cue 边界记录可见字幕同步误差，已缓存目标 ≤250 ms；模型等待另计 |
| 全屏／影院／播放器替换／广告 | 字幕仍在正确容器；广告期间不显示正片字幕；退出后清理旧容器 |
| 长视频、空响应、格式变化、429、超限 | 不影响原生播放；无自动无限重试；明确区分无字幕与读取失败，缓存和请求有界 |
| 导航迟到响应、模型失败、关闭／更新 | 不串视频／轨，不残留旧译文；恢复原生显示；没有后续模型请求 |
| 真实连续翻译 | 使用捕获到的实际字幕连续播放并跳到缓存外，记录获取、翻译、显示三段耗时；不能复用自制文本计时作为通过证据 |

这些是下一原型的验收要求，本轮没有执行或标记通过。现有证据足以支持实现选型；“稳定获取”和“替换显示已在 Sayvia 实站可用”仍须分别过关。
