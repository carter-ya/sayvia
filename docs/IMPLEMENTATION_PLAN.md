本计划把 MVP 拆成可以逐层 review、验证和合并的 PR stack。编号 S00 至 S12 是计划标识，不是 GitHub PR 号码。首次托管只建立最小 main 基线，并为现有文档开一个 PR；未来层在实际开发时创建，不提前创建空分支或空 PR。

## 1 实施原则与完成定义

每层围绕一个可说明的行为或基础能力，附带与其风险相称的测试。基础层可通过模拟页面或模拟 API 验证，不要求每个 PR 都有完整产品界面；但必须存在可复现的验证路径。

新 PR 的 review diff 只应包含相对其直接依赖的新变化。依赖未合并时，base 指向依赖分支；依赖已经合并时，base 指向最新 main。通常最多保持三层未合并 PR，避免底层修改在长链中反复传播。2026-11-01 调度例外：当已确认远程 CI 仅在排队、上游最新提交已完成无问题审核，而后续层已经实现并通过本机检查时，可以先为其建立独立 PR 并触发审核，避免 CI 调度阻塞代码问题发现；这不是合并豁免。每层仍只展示相对直接依赖的 diff，发现底层修复必须逐层传播并对改变的 head 重新审核，最终严格按依赖顺序、最新 head 审核和 CI 成功后合并。

通常以约 300 至 800 行手写实现作为单层 review 大小参考，测试、公开样例与锁文件单独说明。这个范围不作为硬性配额；一层同时引入多个互不依赖的行为或明显超出 review 能力时，拆成有明确依赖的子层，例如 S04a 与 S04b，并更新此计划。不得为了压缩行数隐藏校验或把测试拖到最后。

状态区分：代码提交、PR 创建、review 通过、合并和阶段验收通过。合并一层不代表模型质量或 M1 已经通过；真实模型验证必须有实际记录，模拟回包不能替代。

## 3 S00 文档与仓库基线

### 范围

最小 main 基线只包含产品简介和忽略规则，使空仓库具备可作为 PR base 的提交。文档分支交付现有 PRD、更新后的技术方案、本计划、文档导航与 PR 描述模板。首版不提交业务代码，不创建许可证或未确定的发布承诺。

### 验证与 review

核对本机提交身份、远程账号和 origin 地址；审阅已确认决策与实现假设是否区分；检查 M1 的真实模型与网页选区问题已经覆盖；确认文档链接、版本引用及 A01 至 A20 的验收映射完整。

提交元数据必须来自本项目正确 Git 身份。README 中的文档导航在文档分支落地；合并 S00 后 main 才具备完整文档。

## 4 S01 工程骨架与质量检查

### 范围

- 初始化单包 pnpm、WXT、React 与 strict TypeScript，锁定 Node、包管理器和依赖版本。
- 建立 background、内容脚本、popup、options 与 offscreen 的最小入口，以及本地 Worker 构建样例。
- 配置 Vitest、ESLint、Prettier 和最小 CI；只引入当前确实运行的检查，不用空测试制造绿灯。
- 确保生产构建不包含开发服务器、远程脚本或调试通道。

主要文件：package.json、pnpm-lock.yaml、wxt.config.ts、entrypoints、基础测试与 .github/workflows。

### 验证与退出条件

约定并实际运行 typecheck、lint、format:check、test 和 build 命令。构建产物可在 Chrome 本地加载，popup 与 options 可打开，Offscreen HTML 和独立 Worker 文件存在。README 记录实际开发与检查命令。

### Review 重点

入口与构建是否正确、最低权限是否克制、开发与发布配置是否分离。此层不实现模型、存储 Key 或完整产品 UI。

## 5 S02 配置与永久 Key

### 范围

实现 LocalStateV1、配置仓库、后台写入队列、数据迁移及最小设置表单。最小表单只用于输入并保存模型信息，后续 S08 扩展正式交互，不另写一次性秘密注入工具。

保存首份 Key 前完成 TRUSTED_CONTEXTS 限制；前端只读取 hasApiKey。保留、替换、删除 Key 的语义明确；更新不清空数据。建立运行时校验和最小配置消息白名单，后续消息按层增加。

### 验证与退出条件

用虚假 Key 验证保存、浏览器重启、后台重启、同 ID 正常更新及旧结构迁移。内容脚本读不到 Key；删除配置清除对应 Key；初始化或迁移失败不以默认配置覆盖原数据。

### Review 重点

Key 不进入网页、日志和同步；更新路径可保留配置；不同服务配置与 revision 不串用。S02 需要验证的永久保存能力不能留到 S11 才首次验证。

## 6 S03 编辑框与草稿保护

### 范围

实现 EditorAdapter、GitHub 常规 Issue／PR 评论框识别、节点绑定、修订号、全文与选区快照、安全替换及一步恢复。使用本地测试页面与合成译文测试底层回写，不依赖模型接口。

支持 IME 边界、用户编辑后再撤回、DOM 重建、SPA 导航、框架回滚以及恢复冲突。页面能力无法确认时降级为复制。所有测试入口只能存在于测试构建或 fixture，不能给网页暴露任意写入接口。

### 验证与退出条件

本地页面能观察到正确的手动提交正文；GitHub 实页验证由测试者在专用测试内容中操作。未改草稿可替换／恢复，改动后的草稿无法被旧任务覆盖，切换焦点不改变目标编辑框。扩展不触发网站提交。

### Review 重点

写入是否进入网站状态、身份与修订校验是否闭环、恢复是否覆盖用户新输入。先交付适配能力与测试，完整翻译 UI 归 S07 和 S10。

## 7 S04 输入语义与格式计划

### 范围

实现 SourceInput 三种来源、DOM 选区提取器、Markdown 原始区间解析、纯文本路径和公共 TranslationPlan。

网页选区以原 Range 和节点祖先识别 code／pre；覆盖代码内部选区、跨链接和跨段落。所有偏移绑定同一规范源串，不读取整页 HTML 或链接隐藏属性。Markdown 与纯文本分别处理，保留代码、URL、用户提及、引用和结构；结果重建与校验由同一计划驱动。

固定首批 12 条公开／自制样例，覆盖三种来源及技术方案规定的语义场景。可翻译片段的输入、预期保护内容和人工参考含义随样例提交。

### 实际拆分

S04a 先交付三种 SourceInput 的严格契约、可见 DOM 选区提取、代码／链接标签／段落语义和选区内存快照。S04b 依赖该契约，交付 Markdown 原始区间解析、纯文本保护、公共 TranslationPlan、重建与格式验证及固定 12 条样例。两层分别记录验证与 review，不在 DOM 层提前引入模型协议。

### 验证与退出条件

自动化 fixture 覆盖 A03、A14、A20，代码 timeout 不因 DOM 提取变成普通词。纯保护内容不请求翻译，普通正文不因保护规则被整体跳过。错误和越界元数据被拒绝，外部格式不能执行脚本。

### Review 重点

DOM 语义是否在纯文本化前保留、源串与索引是否一致、格式计划是否便于真实模型使用。若 DOM 与 Markdown 两部分 diff 过大，应拆为 S04a、S04b。

## 8 S05 模型协议与早期真实验证

### 范围

实现 OpenAI／DeepSeek preset、Chat Completions adapter、Base URL 规范化、模型能力字段、响应完成状态和错误映射。请求地址只能来自保存配置；拒绝重定向，不自动重试或切换服务商。

引入可复用的小样本评估入口。使用公开或自制样例，通过实际模型运行分段、请求、重建和格式校验全过程；不能只测“模型返回了某句话”。不在代码、配置模板或 CI 中写入真实 Key。

### 验证与退出条件

本地模拟 API 验证 URL 路径前缀、鉴权、空响应、截断、429、超大响应、无效 JSON、缺失片段与重定向。OpenAI、DeepSeek 各选择一款计划支持的模型，跑 S04 的同组 12 条样例，按技术方案记录首轮结构成功率、保护内容、译文人工判定及耗时。

真实算法验证应在搭建完整执行环境和产品界面前开始。若 Key 或服务不可用，此层可提交可复现工具供 review，但真实验证仍标记未完成，不能凭模拟测试宣告 M1 通过，也不能越过本层的算法门槛开展 M2。

### Review 重点

兼容性声明是否受测试支撑；JSON 片段约束是否损伤语序与自然度；失败是否被真实记录。必要时先调整算法，更新相关设计，再进入依赖其结果的后续开发。

## 9 S06 执行环境与任务生命周期

### 范围

实现后台任务代理、Offscreen 生命周期管理、真实 Dedicated Worker、请求执行、超时和取消。Offscreen 使用 WORKERS 用途且确实承担 Worker 任务。

每标签页互斥、taskId 幂等、任务路由、无正文 session 索引、结果确认和迟到结果丢弃一并实现。后台重启只查询现有执行任务，不重发模型请求，不恢复快速覆盖资格。

### 实际拆分

S06a 先交付 Offscreen 内部执行器与真实 Dedicated Worker：沿用 S05 模型协议，Worker 只接收源文／模型候选，Key 与网络请求留在 Offscreen。使用 Offscreen 主动建立的内部 Port，避免携带 Key 的开始命令广播到扩展界面；不增加默认网站权限。S06b 再接入后台互斥、来源校验、按保存配置读取凭证、主机权限、生命周期串行锁和 session 恢复。创建／取消／关闭竞态及 35 秒真实延迟与后台重启在 S06b 集成验证；S06a 不宣称完整执行链路已完成。

### 验证与退出条件

模拟 API 验证 35 秒延迟响应头、60 秒截止、取消、START／CANCEL 乱序、后台重启、执行器丢失，以及两个标签页同时创建或结束执行环境。关闭 DevTools 后仍通过，空闲时没有保活轮询。

Offscreen 不适用时使用技术方案中可见扩展页的回退设计，并在本层更新架构与验证记录，不能只更换 createDocument 的用途字符串绕过问题。

### Review 重点

资源释放、来源校验和跨任务隔离。真实模型质量工具复用 S05；此层主要使用模拟 API 验证执行控制，不重复消耗完整质量测试预算。

## 10 S07 最小闭环与 M1 验收

### 范围

连接 S02 至 S06，交付最小设置入口、页面翻译按钮和一个简单预览面板，跑通阅读与写作的真实流程。最小面板支持预览、复制、替换、恢复和取消，不包含完整偏好与 UI 润色。

读取真实 DOM 选区与编辑框快照，通过受控执行器完成翻译与校验，再回到原文档。保持各输入提取路径、源文修订和模型任务状态贯通。

### 验证与退出条件

逐项完成技术方案 M1 清单，并新增 docs/validation/M1.md 记录证据：构建版本、浏览器、服务与模型、算法版本、实际测试命令、结果及未通过项。公开报告只使用公开／自制样例，不含 Key、浏览器配置文件或私有仓库 URL。

S05 的真实模型记录只有在算法与模型配置未改变时才可复用；在实际扩展链路中至少补验每种输入来源和两家服务的代表场景。发生算法或协议变化时重跑固定样例，不以不同版本拼凑通过结论。

M1 通过条件以技术方案为准：每款 12 条固定样例格式与保护均通过、无严重语义错误、至少 10 条可直接使用或仅需轻微调整、有效执行在 60 秒内完成，并完成草稿、永久 Key 和生命周期验证。自动技术验证失败时，不开始 S08 至 S10。2026-10-31 用户明确授权继续开发，将真人语义审阅和真实 GitHub 手动提交验收移至正式发布前；两项仍必须完成，不因开发继续或 PR 合并视为通过。

### Review 重点

这是否是同一条真实链路，而非多个互不相连的演示；证据能否支持阶段退出；真实回写和未改动草稿保护是否一致。

## 11 S08 完整设置与弹窗

按独立行为拆为 S08a（偏好与连接测试服务）、S08b（正式模型设置与连接测试 UI）、S08c（语言主题偏好、权限与数据清理）、S08d1（会话草稿服务）、S08d2（正式弹窗与手动翻译）。各层先提交相应测试，再按相同审核流程合并。S08a 先提供受限后台接口，S08b 接通正式设置交互；连接测试复用已有执行器的权限、并发、取消和截止规则，绑定配置版本，不能以修改前的成功结果证明修改后的配置可用。

### 范围

在 S02 最小设置上完善多份模型配置、默认模型、连接测试、语言、主题、站点与 API 权限管理。更新配置后测试状态失效；空 Key 输入保留已有 Key。

完成弹窗概览、当前页识别、手动粘贴翻译与 session 临时草稿。关闭再打开弹窗不丢失当前会话草稿或错误绑定其他标签页任务；清除全部本地数据说明后果并按确认范围清理。

### 验证与退出条件

覆盖 A01、A02、A13、A16、A19 的正式交互。拒绝权限仍能手动翻译，撤销权限取消对应任务。不同配置修改、删除和测试并发时不误用凭证。

### Review 重点

用户能否独立完成首次配置，权限申请是否由明确操作触发，永久保存与删除语义是否可理解。

## 12 S09 阅读体验与触发入口

2026-11-01 用户明确要求：选中文字后出现浮标，点击即在页面浮窗开始翻译并显示结果，不通过浏览器工具栏作为日常主路径。该项优先于 S08d 手动弹窗入口；网站首次授权后自动注入，选区事件只显示图标，不自动发起付费请求。工具栏作为备用入口保留。

### 实际拆分

## 16 Stack 操作与 Review 约定

### 16.1 建立与提交

开始一层前检查工作区、远程和直接依赖。只在已有实现基础上创建下一层分支；每个提交围绕具体变化，提交前检查暂存范围、密钥与个人机器路径。

提交署名通过仓库级 user.name 和 user.email 配置，保留全局与其他项目配置不变。每位贡献者使用自己的身份，不能照抄其他人的署名。推送身份与提交身份分别验证：登录正确账号不代表提交元数据正确。

典型检查：

```sh
git status --short --branch
git remote -v
git config --show-origin --get user.name
git config --show-origin --get user.email
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
```

### 16.2 创建与评审

有实际 diff 和验证结果后创建 PR。仍有待完成的实现或检查时使用 draft；实现与本层自动检查完成后可直接进入 review，以便触发 Codex 审核。PR 描述说明用户触发的问题、最终行为、计划层号、依赖与后续层、验证证据及未验证边界。不能把预期检查写成已运行。

创建 PR 后必须自动增加一条顶层评论 `@codex review`，显式触发 Codex 审核；不能仅凭创建 PR、CI 通过或暂无评论判断已经审核。后续修复推送改变 head 后，重新触发并核对审核结论对应最新提交，避免使用过期结论合并。

review 通过且该层验证完成后转为可合并状态。M1 与发布质量门槛通过有单独的记录，不因某个 PR 获得批准而自动达成。review 优先关注模块边界、可观察结果、数据安全和维护成本，不把个人风格偏好当作阻塞项。

### 16.3 上游修改与合并

底层改动后，先把更正带到直接子层，再依次更新后续层并跑受影响检查。不要将整条 stack 的所有改动挤进底层 PR。推送自己的 review 分支如需改写历史，应使用明确分支与 --force-with-lease，禁止 force 推送 main。

按 S00、S01 等依赖顺序合并。优先采用保留祖先提交的 merge commit，降低下游重排成本。合并须有用户授权；当前用户已授权在最新提交的 Codex 审核无问题且检查通过后合并并推进后续层，不修改仓库合并设置。

上游已用 merge commit 合入 main 时，将下一层 PR base 改为 main 并核对 diff。如果上游通过 squash 或 rebase merge 改写了提交身份，先记录旧依赖 tip，再只把本层新提交移到新 main；不能简单改 base 后保留重复的祖先 diff。

有多层下游时，可使用以下有界重排思路。实际执行前核实分支名与提交范围，不能原样复制占位值：

```sh
git fetch origin
git rebase --onto origin/main OLD_PARENT_TIP CHILD_BRANCH
```

重排下一层前记录其旧 tip，以便只移动后继的新增提交。逐层复查 PR diff、检查与冲突解决结果；不依赖 GitHub 自动改 base 就认定 stack 已正确重排。

### 16.4 CI 与外部调用

新增检查必须在当前层真实可运行。模拟 API、公开样例和浏览器 fixture 进入普通 CI；真实模型验证单独手动触发并记录配置、调用次数和结果。CI 及报告不得包含真实 Key、浏览器会话目录或私有草稿。任何暂缺的实际验证必须明确列出，不能用模拟结果替代。
